# Approach write-up

**What I prioritised.** The brief weights AI integration and architecture highest, so I built the core ticket loop first (author raises a ticket, AI triages it, admin opens it and gets a grounded draft, admin replies, author sees it live) and made that loop robust before adding polish.

**AI design.** I split the work into two calls. Triage is cheap and automatic: a small model with a tiny prompt returns a validated JSON category and priority, and a code-level policy rule enforces the knowledge base (ISBN errors are never below High). Drafting is lazy and expensive: it only runs when an admin opens a ticket, includes only that category's policy and one style example, and is cached. The key idea is that **numbers and dates are computed in code** (royalty totals, the ₹1,000 threshold, the next payout date, "never paid / overdue" flags) and handed to the model as facts, so the model writes the tone and structure while the facts stay correct. That matters for the awkward records in the dataset: never-paid authors, balances below the payout threshold, and two books still in production.

**Resilience.** Ticket creation never depends on the LLM. Timeouts, retries with backoff, a concurrency cap and a circuit breaker protect against rate limits. When AI is down, keyword rules still sort the queue, the admin sees why, and can retry or write the reply by hand. Admin overrides always win over AI values.

**Trade-offs.** I chose SSE over WebSockets (one-way updates, simpler to operate, auto-reconnect) and an in-memory event hub over Redis (fine for one instance, noted as the first scaling step). Attachments are UI-only as the brief allows. I used a simple, clean UI rather than spending time on visual polish.

**Taking it to production.** (1) Move the event hub, rate limits and AI breaker to Redis and run the AI work through a queue. (2) Add email/WhatsApp notifications on the same events. (3) Real file uploads with scanning. (4) httpOnly-cookie sessions, password reset, audit log of admin actions. (5) Retrieval over the full KB with per-category versions once policies grow beyond a few pages. (6) An evaluation set of real tickets to measure classification accuracy and draft acceptance (the `aiAssisted` flag on replies is already captured), plus tracking edit distance between AI draft and sent reply to improve prompts. (7) SLA timers and auto-escalation of Critical tickets that sit unassigned.
